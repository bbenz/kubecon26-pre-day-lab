# Skillable deployment

Everything needed to run the KubeCon AKS capture-the-flag lab on [Skillable](https://www.skillable.com/):
a lab VM image, life cycle actions (LCAs) that build each attendee's environment in the begin state, and the
attendee content (the lab instructions, and the attendee folder on the VM), generated from the challenges without
the solutions. Modeled on the LAB723 (Ignite 2026) Skillable artifacts, with a much shorter prepare LCA.

| Folder or file | What | Runbook |
| --- | --- | --- |
| [`vm-image/`](vm-image) | The VM image setup script, run by hand in the lab VM, and its paste-in bootstrap | [VM-IMAGE-RUNBOOK.md](vm-image/VM-IMAGE-RUNBOOK.md) |
| [`lca/`](lca) | The prepare and readiness gate LCAs, the worker they run, a test-only access LCA, and a manual begin-state bootstrap | [LCA-RUNBOOK.md](lca/LCA-RUNBOOK.md) |
| [`skillable lab steps.md`](skillable%20lab%20steps.md) | The lab instructions to import into Skillable Studio. Generated: don't edit it. | [Attendee content](#attendee-content-and-solutions) |
| [`attendee/`](attendee) | The sources of the attendee content: the lab instructions' template, and the attendee folder's README, `check.ps1`, and `reset.ps1` | [Attendee content](#attendee-content-and-solutions) |
| [`build-attendee-content.ps1`](build-attendee-content.ps1) | Generates the lab instructions and the attendee folder from the challenges, and checks them for solutions | [Attendee content](#attendee-content-and-solutions) |
| [`make-bootstraps.ps1`](make-bootstraps.ps1) | Regenerates both bootstraps after a script change | |

## How a lab launches

```mermaid
sequenceDiagram
    participant S as Skillable
    participant VM as Lab VM (image)
    participant W as Worker (SYSTEM)
    participant AZ as Attendee's subscription
    S->>AZ: Pre-Build: resource group, cloud portal user (Contributor)
    S->>VM: Start the VM; automatic sign-in; VS Code opens C:\lab-resources
    S->>VM: First Displayable: prepare LCA (service principal)
    VM->>VM: git clone the repository at RepoRef, into a folder only SYSTEM and administrators can open
    VM->>W: Scheduled task: Invoke-CtfLabSetup.ps1 -Mode Prepare
    W->>VM: C:\lab-resources from the clone, without the solutions; delete the clone
    W->>AZ: deploy.ps1: AKS Automatic + challenge services, 10 challenges broken
    W->>AZ: Portal user: AKS RBAC Cluster Admin, Monitoring Data Reader
    W->>VM: kubeconfig (azurecli), browser sign-in for az, readiness gate
    S->>VM: Assigned to attendee: readiness gate LCA
    VM->>VM: Gate again; delete the service principal's profile; clear PowerShell logs
    Note over VM: Attendee: az login (Temporary Access Pass), then the challenges
```

| Order | Event | Action | Time |
| ---: | --- | --- | --- |
| 1 | Pre-Build | Skillable creates the resource group, the cloud portal user, and the VM from the committed image | Skillable |
| 2 | First Displayable | **Prepare LCA**: the attendee folder `C:\lab-resources` (no solutions), the begin state of all ten challenges, the portal user's roles, the lab user's kubeconfig and Azure CLI, optionally Inspektor Gadget, and the readiness gate | 20 to 30 minutes (20 in testing) |
| 3 | Running Preinstance Assigned To User | **Readiness gate LCA**: the gate again, then removes the service principal from the VM | About a minute |
| 4 | Optional, at or after assignment | **Leaderboard LCA** (generated by `leaderboard/setup.ps1`): registers the VM with the event leaderboard | Seconds |
| 5 | Tearing Down | Skillable deletes the resource group and the cluster | Skillable |

## The lab VM

The image setup script installs every tool from the lab design's VM prerequisites, verified against
published checksums or signatures:

- Azure CLI (2.86 or later) with the **aks-agent** extension, and **k8s-extension**
- **kubectl**, **kubelogin**, and **Helm**
- **GitHub CLI**
- **AKS desktop** and **Inspektor Gadget** (`kubectl gadget`; the prepare LCA can add its AKS cluster extension,
  off by default: see the LCA runbook)
- **VS Code** with **GitHub Copilot** (built into current VS Code) and the **Kubernetes** and **AKS** extensions,
  with **AKS-MCP** set up as a user MCP server
- **PowerShell 7**, **Git** (Git Bash), **Terraform**, **ingress2gateway** (C2), and **WSL** with Ubuntu and the
  Azure CLI, kubectl, kubelogin, and Helm inside it
- The attendee folder `C:\lab-resources`, opened by VS Code at sign-in, which the prepare LCA fills at each launch.
  The image has no copy of the lab repository, because the repository has the solutions.

Two prerequisites aren't VM settings:

- **Azure Kubernetes Service RBAC Cluster Admin**: AKS Automatic turns off local accounts, and Owner isn't
  enough. The prepare LCA gives it to the cloud portal user, and deploys (and scores) as the service principal,
  which `deploy.ps1` gives the same role.
- **MCP servers in Copilot**: a GitHub organization or enterprise policy, off by default, for Copilot Business
  and Enterprise seats. An owner of the organization that provides the attendees' Copilot seats turns it on
  (organization **Settings** > **Copilot** > **Policies** > **MCP servers in Copilot**: **Enabled**). See the
  [LCA runbook](lca/LCA-RUNBOOK.md#before-you-start).

## Readiness checklist for an event profile

- [ ] VM image built and committed with the current setup script ([VM image runbook](vm-image/VM-IMAGE-RUNBOOK.md))
- [ ] Profile: cloud subscription pool; resource group `ResourceGroup1` with **Override Region** (AKS Automatic,
      and `gpt-6-luna` Global Standard for C4); portal user `User1` with Contributor
- [ ] Access control policy allows the resource types in the [LCA runbook](lca/LCA-RUNBOOK.md#before-you-start)
- [ ] Quota per lab subscription: about 16 to 24 D-family vCPUs, and 50,000 TPM of `gpt-6-luna` Global Standard
- [ ] Prepare and readiness gate LCAs added ([settings](lca/LCA-RUNBOOK.md#add-the-lcas-in-skillable)), with
      `RepoRef` set to the event's tag, and a pool admin has turned on the prepare LCA's cloud credentials
- [ ] Lab instructions imported from [`skillable lab steps.md`](skillable%20lab%20steps.md), generated from the same
      commit as `RepoRef`
- [ ] A test launch passes the readiness gate, `C:\lab-resources\check.ps1 -Quick -NoReport` shows every challenge
      **NOT PASSED**, and `C:\lab-resources\reset.ps1 c1` works as the attendee
- [ ] Preinstances with at least 45 minutes of lead time, plus spares
- [ ] Copilot seats for attendees, with the **MCP servers in Copilot** policy on
- [ ] Decision on a model for `az aks agent` ([LCA runbook](lca/LCA-RUNBOOK.md#github-copilot-aks-mcp-and-az-aks-agent))
- [ ] Optional: the event leaderboard ([leaderboard/README.md](../leaderboard/README.md))

## Attendee content and solutions

The repository is the single source of truth. Each challenge's `README.md` is what attendees read; its
`SOLUTION.md`, the README's feasibility assessment, and `challenge-end-state` are for proctors. Attendees get
content generated from the same files, so a change to a challenge is made once:

| What attendees get | Where | Built by |
| --- | --- | --- |
| The lab instructions: introduction, getting started, tools and tips, checking and resetting, a page for each challenge (from its `README.md`), and a wrap-up | [`skillable lab steps.md`](skillable%20lab%20steps.md), imported into Skillable Studio | `build-attendee-content.ps1 -LabSteps`, from [`attendee/lab-steps-template.md`](attendee/lab-steps-template.md) and the challenge READMEs |
| The attendee folder: each challenge's `README.md` (the same text as its instructions page), manifests, and settings; `deploy.ps1` and its PowerShell module; the scoring scripts; and [`README.md`](attendee/README.md), [`check.ps1`](attendee/check.ps1), and [`reset.ps1`](attendee/reset.ps1) | `C:\lab-resources` on the lab VM | `build-attendee-content.ps1 -Destination`, which the prepare LCA runs at each launch |

From each challenge `README.md`, the script removes the header table's **Round** and **Walkthrough** rows and the
feasibility assessment, points the check and reset commands at `C:\lab-resources\check.ps1 <id>` and
`C:\lab-resources\reset.ps1 <id>`, and notes that the VM already has `ingress2gateway`. In the lab instructions,
the hints become collapsible sections. Every other file in a challenge folder goes to the attendee folder as it
is, except `SOLUTION.md`, and the comments in `*.env` files (A4's says what its fault is). The script fails if the
result mentions solutions, a walkthrough, facilitators, the end state, or the feasibility notes, links to a file
that attendees don't have, or links to the repository.

On the VM, the prepare LCA clones `RepoRef` into `C:\ProgramData\kubecon-ctf-lca\repo` (only SYSTEM and
administrators can open it), builds `C:\lab-resources` from it, and deletes the clone before it deploys anything.
The VM image has no copy of the repository. The readiness gate fails if a clone, a `SOLUTION.md`, or the end
state is in `C:\lab-resources`, `C:\LabFiles`, or the LCA's folder; so does the image setup script's verification.

**When you change a challenge,** edit its `README.md` (and `SOLUTION.md`) in the repository, run
`./skillable/build-attendee-content.ps1 -LabSteps`, and then `./skillable/build-attendee-content.ps1 -Check`, which
fails if the instructions are out of date or if anything attendees get has solution content. Commit both, tag the
release, set the prepare LCA's `RepoRef` to the tag, and import the new instructions into Skillable Studio.

**What this doesn't hide:**

- **The public repository.** Anyone who finds it can read `SOLUTION.md`. For stronger protection, make the
  repository private and publish only the attendee folder: `build-attendee-content.ps1 -Destination` builds
  everything that the begin state needs (the LCA deploys from it), so the LCA could download that folder as a
  release asset of a public repository instead of cloning this one. That needs a small change to the prepare LCA
  and the worker (not made).
- **How the lab checks and deploys challenges.** `C:\lab-resources` has the scoring scripts, which show what's
  checked (the check's output names each criterion anyway), and the deployment scripts and manifests, which show
  each challenge's starting state, such as C4's model deployment name in `deploy.ps1`. Attendees are
  administrators on the VM, so file permissions can't hide them. If a leaderboard with prizes makes that matter,
  consider Skillable's activity-based assessments, whose scripts are kept in the lab profile instead of the VM.

## Test results (2026-11-03)

Tested outside Skillable, in Azure (westus3), as close to a Skillable launch as possible: a clean Windows 11 Pro
26H2 VM (D4s_v5, automatic sign-in), a resource group with a test service principal that was Owner of that resource
group only (no Microsoft Graph permissions), and a user with Contributor on it as the cloud portal user.

| Step | Result |
| --- | --- |
| Image setup script, typed in as the lab user (elevated), via the bootstrap's payload | 12 items READY: first pass 12 minutes, restart for WSL, second pass about 6 minutes (Ubuntu on WSL 2 with the Linux tools). Every verification row passed, except the Skillable integration service, which a plain Azure VM doesn't have. A rerun on a finished image takes 2.5 minutes. |
| `-Finalize -NoShutdown` | Verified, removed credentials, caches, history, and `C:\LabSetup`; kept the Azure CLI extensions and the lab repository |
| Prepare LCA, as SYSTEM through `powershell.exe`, with the tokens filled in | Fetched `RepoRef`; the worker deployed all ten challenges in 18.5 minutes (cluster 11.5 minutes), gave the portal user its three roles without Microsoft Graph, wrote the lab user's kubeconfig, and set up the lab user's Azure CLI. About 20 minutes in all without Inspektor Gadget. |
| Readiness gate LCA, as SYSTEM | Passed in 18 seconds. Before it ran, the Windows PowerShell Operational log had one event with the service principal's application ID **and its secret** (the prepare LCA's text); afterward, the worker's Azure CLI profile was gone and no event had the application ID. |
| `scoring/verify.ps1` as the portal user | All ten challenges **NOT PASSED**, as designed for the begin state |

Changes from the test: Copilot Chat is built into VS Code 1.144 (the image now checks for it instead of installing
it); the Linux Azure CLI in WSL (WSL's appended Windows PATH hid it); a Windows widgets policy value that can't be
rewritten; Inspektor Gadget became opt-in (its DaemonSet can't run on AKS Automatic's hosted system nodes, so the
extension stayed in Creating and held the LCA for 17 minutes); and the deployment scripts now read the signed-in
identity's object ID from its token, because the service principal couldn't read Microsoft Graph.

Not tested outside Skillable: the pool's secure-token handoff, Skillable's own script runner, the lab client's
console (VS Code and Edge opening at sign-in), the attendee's `az login` with a Temporary Access Pass, and the
manual begin-state bootstrap (it needs an interactive browser sign-in).
